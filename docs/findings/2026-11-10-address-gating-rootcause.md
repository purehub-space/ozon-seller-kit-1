# Ozon PDP 库存字段消失的真正根因：配送地址粒度

> 记录时间：2026-11-10
> 结论一句话：**PDP 拿不到库存不是 IP 降权、不是反爬、不是配额，而是收货地址只到城市级。**

## 一、现象

同一端点 `GET /api/entrypoint-api.bx/page/json/v2?url=/product/{sku}/`：

| 会话状态 | 响应体 | freeRest / maxItems / stockNumber |
|---|---|---|
| 地址仅「Москва」，未填街道 | 142,7xx B | **全部为空**（二次编码深搜也是 0 处） |
| 地址填到「Москва, Тверская улица, 1」 | **170,1xx B** | **freeRest=193 / stockNumber.text='193'** |

体积差 ~28 KB，丢的正是库存区块。

## 二、被排除的假设（都做过对照实验）

| 假设 | 实验 | 结果 |
|---|---|---|
| IP 降权 | 配额恢复后连发 4 条路径 | 全部 200，库存字段仍 0 |
| 商品缺货 | 用列表页 maxItems=194/130/1 的在售商品逐个开 PDP | PDP 仍显示「Товара нет в продаже」、无库存 |
| 城市设置错 | 页面头部检查 | 已显示「Москва」 |
| 响应被裁 | 二次编码深搜 `widgetStates` | 0 处，不是解析问题 |
| 参数缺失 | `layout_container` / `layout_page_index`（正确 URL 编码） | 144,725 / 51,135 B，仍无库存 |
| 浏览器不够真 | Camoufox（真 Firefox 内核） | 同样无库存 |

## 三、决定性证据

1. 列表页 HTML 里 `quantityButton.maxItems` 一直存在（194/130/1/996/1010…），**说明库存数据本身没被删**。
2. 设地址后 PDP 截图出现「Распродажа **194 единицы осталось**」+「**В корзину**」+「Доставим 14 ноября」，与列表页 maxItems 完全一致。
3. 设地址后同一 SKU 的 fetch 返回 170,182 B，`freeRest=194`。

## 四、机制

Ozon 的 PDP 是按「**能否配送到你的具体收货地址**」计算可售与库存的。只有城市级地址时无法计算配送可达性，页面按「不可购买」渲染，服务端也就不返回库存字段（省钱+省逻辑）。列表页卡片走另一套逻辑，所以一直在给 `maxItems`。

**因此：这不是反爬对抗问题，是会话状态（地址）问题。** 之前所有「换 IP / 加指纹 / 降频 / 换票」的尝试注定无效。

## 五、地址可持久化

设一次地址后导出 cookie（11 条），**仅用 cookie 新建会话不重设地址，PDP 直接返回 170,250 B 带库存**。

→ 所以每个采集会话只需在 mint 时设一次地址，后续请求全部带库存。

## 六、字段与口径

| 字段 | 位置 | 说明 |
|---|---|---|
| `quantityButton.maxItems` | 列表页 HTML / `widgetStates` | 前台数量控件上限，SKU 在同节点 `updateCartAction.id` |
| `freeRest` | `webAddToCart-*` 内（二次编码 JSON） | 800 以上被封顶为 800 |
| `stockNumber.text` | `bigPromoPDP-*` | 促销位真值，>2000 时唯一可信 |
| `stockText.text` | 同上 | 「N единиц осталось」文案 |

| 区间 | maxItems | freeRest | 文案 |
|---|---|---|---|
| <800 | 准 | 准 | 准 |
| 800–2000 | 准 | **封 800** | 准 |
| >2000 | **封顶 2000** | 封 800 | **只有文案是真值** |

## 七、通道对比（设过地址之后）

| 通道 | 端点 | 首字节/吞吐 | 备注 |
|---|---|---|---|
| 浏览器页内 fetch | `page/json/v2` | 8–9 页/秒 | Camoufox 会 `channel error` 崩溃，需 setsid |
| **curl_cffi HTTP** | 同上 | 5.3 页/秒（conc=30） | **不需要浏览器**，只依赖 cookie 里的地址 |

HTTP 通道黄金参数：`impersonate="firefox147"`，headers 用浏览器实发原串（含 cookie，~1,350–1,382 字符），**严禁** `cookies=dict` 重组。

## 八、运维要点

1. **mint 必须设地址**，否则拿到的全是 142 KB 精简版且不报错（静默失败，账面成功率好看但数据为空）。
2. 每次 rotate（800 次）remint 时要重新设地址，日志需打印「地址设置 成功/失败」。
3. 请求量必须设闸门：历史累计 2.7 万请求即触发降权，限速建议 ≤2 页/秒（7,200/小时）。
4. 跑高并发前 `ulimit -n 65535`（本机默认 2048，100 并发会 `curl (35) Recv Failure`）。
5. 同 IP 只允许一个活跃浏览器会话；HTTP 通道与浏览器不要同时跑。

| 脚本 | 用途 |

## 十、限流阈值实测（2026-11-10 16:00–16:15）

### 10.1 速率不是瓶颈，累计量才是

| 时段 | 方式 | 结果 |
|---|---|---|
| 15:27–15:42 | Camoufox conc=15，8–9 页/秒 | 跑通 4,380 条后 `channel error`（进程侧问题） |
| 16:03–16:05 | curl_cffi conc=30，**5.3 页/秒** | **403=0**，360 请求全成功 |
| 16:10 起 | 同上 | **403=120/120，全部是 `challengeURL`** |

关键：**同样的并发和参数，5 分钟前全成功，5 分钟后全 403。**

### 10.2 单发串行也 403

`curl_cffi` 单发一个请求（无并发）→ 403 / 7,299 B / 含 `challengeURL`。

**排除并发因素。**

### 10.3 新 mint 的干净会话同样 403

`mint_once.py` 开全新 Camoufox context、地址设置成功、cookie_len=1362，立即验证 → **403 / 6,419 B**，无库存字段。

**排除「cookie 被标记」因素。**

### 10.4 结论：这是出口 IP 级累计配额

| 日期累计请求 | 数据 |
|---|---|
| stock_obs 200 条 | 13,018 |
| review_obs 全部 | 9,758 |
| 含失败重试 | ~30,000 |

**约 3 万请求/出口 IP/天 即触发 challenge 层。**这与早期「2.7 万请求触发降权」的历史记录一致，是同一机制的不同表现。

### 10.5 因此的吞吐上限

| 约束 | 数值 |
|---|---|
| 单日请求上限（保守） | 25,000 |
| 12 小时可用 | 25,000 |
| 折合速率 | **≤0.58 页/秒**（约 2,100/小时） |
| 跑完 29,823 一轮 | 约 14 小时 |

**12 小时内跑不完一整轮**，这是出口配额决定的硬约束，不是代码问题。

### 10.6 三条可选路线（**需要明确的授权前提**）

| 路线 | 说明 | 前置 |
|---|---|---|
| A. 慢跑单轮 | 0.58 页/秒，14 小时一轮 | 无（当前直连可做） |
| B. cookie/会话轮换 | 每 ~400 请求换会话 | **无效**——实测换 cookie 仍 403（10.3），因为限的是 IP 不是票 |
| C. 多出口 IP | 才能突破 3 万/天 | 需要额外出口，**用户已三次否决代理** |

所以当前唯一可行的是 **A：长期低速直连**。任何「提高吞吐」的方案都会撞回 3 万这个天花板。

### 10.7 恢复方法

触发后需冷却（实测需数十分钟到数小时）。恢复判据：单发 `/product/2474366854/` 返回 **200 且 ≥155 KB**（142 KB 说明地址态丢了，`challengeURL` 说明还在冷却）。
